# Архитектура CRM для сервиса ремонта телефонов (по мотивам ROApp)

## 1. Цель
Разработать легковесную CRM, объединяющую:
- управление клиентами и устройствами,
- управление заказами (ремонт),
- складской учёт запчастей,
- финансовый учёт (доходы, расходы, прибыль).

## 3. Ключевая логика (как в ROApp)

### 3.1 Универсальный поиск при создании заказа
Одна строка поиска ищет **одновременно** по полям:
- `clients.name`
- `clients.phone`
- `devices.imei`
- `devices.serial_number`
- `devices.brand`
- `devices.model`

**API эндпоинт:** `GET /search?q=...`

**Алгоритм (псевдокод):**
```python
def universal_search(q):
    results = []
    clients = db.query(Client).outerjoin(Device).filter(
        Client.name.ilike(f'%{q}%') |
        Client.phone.ilike(f'%{q}%') |
        Device.imei.ilike(f'%{q}%') |
        Device.serial_number.ilike(f'%{q}%') |
        Device.brand.ilike(f'%{q}%') |
        Device.model.ilike(f'%{q}%')
    ).distinct().all()
    
    for client in clients:
        devices = db.query(Device).filter_by(client_id=client.id).all()
        results.append({'client': client, 'devices': devices})
    
    return results
    
    Поведение:

Если найдено устройство по IMEI – возвращаем клиента и это устройство (прямой матч).
Если найден клиент по телефону – показываем его и список его устройств.
Если найдено по имени – показываем всех подходящих клиентов.
Если ничего не найдено – предлагаем создать нового клиента и новое устройство.
3.2 Создание заказа

POST /orders

Тело запроса:

json
{
  "client": { "name": "Иван", "phone": "+79991234567" },
  "device": { "brand": "Apple", "model": "iPhone 12", "imei": "123456789012345" },
  "issue_description": "Не включается",
  "master_id": 2
}
Либо если выбран существующий device_id:

json
{
  "device_id": 101,
  "issue_description": "Разбит экран",
  "master_id": 2
}
Что делает бэкенд:

Если передан device_id – проверяет существование устройства и его клиента.
Иначе – ищет клиента по телефону/имени, создаёт, если нет; затем создаёт устройство.
Создаёт заказ со статусом new.
Записывает начальную запись в order_history.

3.3 Смена статуса заказа

PATCH /orders/{id}/status

Тело: { "status_slug": "repair", "comment": "Начал ремонт" }

Действия:

Проверить, что новый статус допустим (логика переходов: например, из new нельзя перейти в completed).
Обновить orders.status_id.
Добавить запись в order_history.
Если новый статус completed – установить completed_at = now().
Если статус waiting_parts – возможно, система проверяет, что нужные запчасти заказаны (опционально).
3.4 Списание запчасти на заказ

POST /orders/{id}/parts

Тело: { "part_id": 5, "quantity": 1 }

Действия (в транзакции):

Проверить остаток parts.quantity >= quantity.
Уменьшить parts.quantity.
Добавить запись в order_parts с текущими закупочной и продажной ценами.
Добавить запись в part_movements (тип outgoing).
Если остаток стал ниже min_quantity – сгенерировать уведомление администратору.
3.5 Финансовый учёт

3.5.1 Приём платежа

POST /payments

Тело: { "order_id": 123, "amount": 2000, "payment_method_id": 1, "is_prepayment": false }

Действия:

Добавить запись в payments.
Обновить orders.prepaid (если это предоплата – увеличить; если доплата – проверяем, что сумма не превышает orders.cost).
3.5.2 Расчёт прибыли по заказу (при завершении)

Функция calculate_order_profit(order_id):

text
income = сумма всех payments.amount по этому заказу
cost_of_parts = сумма (order_parts.purchase_price_at_moment * quantity_used)
labour = income - cost_of_parts   # валовая прибыль без учёта зарплаты мастера
pure_profit = labour - (зарплата мастера, если отнесена к заказу через expenses)
Итоговая прибыль может храниться в отдельном поле orders.profit или вычисляться на лету.

3.5.3 Отчёт о прибыли за период

GET /finance/report?from=YYYY-MM-DD&to=YYYY-MM-DD

Расчёт:

Доходы = сумма payments.amount по заказам, у которых completed_at в периоде.
Расходы = сумма expenses.amount за период + сумма purchase_price_at_moment * quantity_used по заказам, завершённым в периоде.
Чистая прибыль = Доходы − Расходы.
4. Роли и права доступа

Роль	Доступ
admin	Полный доступ ко всем модулям, отчётам, пользователям, настройкам
master	Видит только свои заказы, может менять статус, списывать запчасти, добавлять диагноз. Не видит закупочные цены.

6. Технические рекомендации по реализации

**База данных:** PostgreSQL (Supabase — dev, чистый PostgreSQL — prod).
**Индексы для ускорения поиска:**

```sql
CREATE INDEX idx_clients_phone ON clients(phone);
CREATE INDEX idx_devices_imei ON devices(imei);
CREATE INDEX idx_clients_name_trgm ON clients USING gin (name gin_trgm_ops);
```

**Транзакции** при списании запчастей и приёме платежей.
**Язык бэкенда:** Node.js + Express + TypeScript.
**Фронтенд:** React + Vite + TypeScript (деплой на Vercel).
**Авторизация:** JWT с ролями.
**Логирование:** все изменения статусов и списания пишутся в историю.
**Миграции БД:** `node-pg-migrate` (SQL-файлы в `apps/api/migrations/`).
**Инфраструктура dev:** без Docker. Supabase (БД) + локальный Express + Vercel (фронтенд).
**Инфраструктура prod:** Docker Compose на VPS (PostgreSQL + API + nginx).
7. Инфраструктура: Supabase (dev) → VPS (prod)

### 7.1 Разработка на Supabase + Vercel

На этапе разработки и MVP **не используем Docker** — он будет только на продакшн-VPS. Вместо этого:

- **База данных** — **Supabase** (облачный PostgreSQL). Не жрёт RAM на локальной машине.
- **Фронтенд** — **Vercel** (бесплатно, авто-деплой из GitHub).
- **API** — локально (`npm run dev`) или на Vercel (serverless functions) / Render / Railway.

Supabase предоставляет готовые сервисы поверх PostgreSQL, которые ускоряют разработку:

- **PostgreSQL** с админкой (Table Editor, SQL Editor)
- **Аутентификация** — встроенный JWT, регистрация, роли через Row Level Security
- **Realtime** — подписки на изменения в БД через WebSocket (статус заказа обновляется в реальном времени)
- **Edge Functions** — serverless-функции (Deno) для вебхуков, алертов, уведомлений
- **Database Webhooks** — триггеры на события БД (например, при низком остатке запчасти → вызов Edge Function)
- **Storage** — хранение фото устройств, актов приёма-передачи

### 7.2 Перенос на VPS (продакшн)

При переходе в продакшн данные и логика мигрируют на **собственный VPS** (например, 1 vCPU / 2 GB RAM). На VPS поднимается Docker Compose с PostgreSQL + Node.js/Express + nginx.

**Что теряется при переезде с Supabase на голый VPS:**

| Функция Supabase | На VPS придётся реализовать вручную |
|---|---|
| **Database Webhooks** (алерт при низком остатке, уведомление о смене статуса) | 🟡 Эмулировать через PostgreSQL `NOTIFY`/`LISTEN` + фоновый worker, либо polling из API |
| **Realtime (WebSocket)** | 🟡 Добавить отдельный WebSocket-сервер (`socket.io`) или использовать polling на клиенте |
| **Edge Functions** (serverless-функции) | 🟡 Перенести в обычные Express-роуты или фоновые workers (Bull / Agenda / pg-boss) |
| **Storage / Buckets** (фото) | 🟡 Хранить в локальной папке `uploads/` или подключить S3 (MinIO / Wasabi / Cloudflare R2) |
| **Auth + RLS** (Row Level Security) | 🟡 JWT остаётся, RLS заменяется middleware в Express |
| **SQL Editor / Table Editor** | 🟡 Использовать pgAdmin, DBeaver или Adminer в Docker |
| **Автоматические бэкапы** | 🟡 Настроить pg_dump по cron |
| **Встроенные метрики / логи** | 🟡 Настроить PM2 + Winston/Pino, опционально Grafana |

### 7.3 Стратегия (чтобы переезд был безболезненным)

1. **Код пишем портабельно** — весь код пишется с прицелом на чистый PostgreSQL. Не используем Supabase-специфичные расширения (кроме `uuid-ossp` и `pgcrypto`, которые доступны везде).
2. **Миграции** — схема БД через `node-pg-migrate` (SQL-файлы), чтобы она была переносимой без привязки к Supabase.
3. **Фронтенд** — сразу на Vercel. При переезде на VPS достаточно перенаправить домен или залить собранный `dist/` на nginx.
4. **Алерты и фоновые задачи** — на этапе Supabase используем Database Webhooks → Edge Functions. При переезде переключаемся на `pg-ipc` (NOTIFY/LISTEN) или очередь задач внутри Express.
5. **Файлы** — абстрагируем слой хранения через переменные окружения: в Supabase → Storage API, на VPS → локальная папка с возможностью переключения на S3.
6. **Экспорт данных** — при переезде делаем дамп Supabase через `pg_dump` и импортируем на VPS.

### 7.4 Ограничения и подводные камни

- **Бесплатный лимит Supabase:** 2 проекта, 500 MB БД, 5 GB Storage, 50 000 строк Realtime, 500k Edge Functions запросов/мес
- **Edge Functions** имеют холодный старт (~500 мс) — не подходят для критичных по времени операций
- **Database Webhooks** не гарантируют exactly-once доставку — нужна идемпотентность на стороне получателя
- **Резервное копирование:** на Supabase автоматическое, но период восстановления на бесплатном плане — до 24 часов. На VPS это настраивается вручную (cron + pg_dump)
- **Row Level Security** работает только внутри Supabase — при переезде на VPS вся логика доступа ложится на Express middleware
- **Миграция данных** — при переезде нужно учитывать, что Supabase использует свои последовательности (sequences) для `serial`-полей; при дампе они сохраняются, но важно проверить
