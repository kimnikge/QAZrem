### 1.2 Проблемы текущей архитектуры

| Проблема | Описание | Влияние |
|----------|----------|---------|
| **Монолитные страницы** | `DashboardPage.tsx` >500 строк, `SettingsPage.tsx` >800 строк, `CreateOrderPage.tsx` >400 строк | Сложно поддерживать, тестировать |
| **Дублирование логики** | Фильтры, пагинация, модалки создания/редактирования повторяются на каждой странице | Много кода, баги копируются |
| **api.ts — один файл** | Все API-вызовы и типы в одном файле (~400 строк) | Трудно найти нужный эндпоинт |
| **Отсутствие общих компонентов** | Каждая страница реализует таблицу/фильтры/модалки по-своему | Не консистентный UI |
| **Нет слоя бизнес-логики** | Роутеры бэкенда содержат и SQL, и валидацию, и бизнес-правила | Смешение ответственности |
| **Нет типов между фронтом и бэком** | Типы дублируются в `api.ts` и роутерах вручную | Расхождения типов |

## 3. План рефакторинга по шагам

### Шаг 1: Разбить `api.ts` на модули

**Сейчас:** один файл `frontend/src/api.ts` (~400 строк)
**Цель:** папка `frontend/src/api/` с файлами по модулям

```
frontend/src/api/
├── index.ts        # re-export всего
├── client.ts       # auth, users
├── orders.ts       # orders, order-groups, search
├── accounts.ts     # кассы, сплиты, перемещения

├── finance.ts      # finance, payments, expenses
```

### Шаг 3: Универсальная таблица (DataTable)

**Сейчас:** `DashboardTable.tsx` жёстко завязан на заказы
**Цель:** универсальный `DataTable<T>` с:

```typescript
interface Column<T> {
  key: string;
  label: string;
  render: (item: T) => React.ReactNode;
  sortable?: boolean;
  sticky?: 'left' | 'right';
  width?: number;
}

interface DataTableProps<T> {
  columns: Column<T>[];
  data: T[];
  rowKey: (item: T) => string | number;
  onRowClick?: (item: T) => void;
  selectable?: boolean;
  compact?: boolean;
  loading?: boolean;
}
```

Переиспользовать в: заказах, контактах, складе, финансах.

### Шаг 4: Универсальная строка фильтров (FilterBar)

## 4. Технический долг — что исправить

### 4.1 Бэкенд

| Проблема | Решение |
|----------|---------|
| SQL-запросы в роутерах | Вынести в `repositories/` |
| Дублирование пагинации | `middleware/pagination.ts` |
| Отсутствие валидации query-параметров | `middleware/validate.ts` + Zod |
| Нет транзакций при создании заказа | `db/pool.ts` → добавить `withTransaction()` |
| Услуги не привязываются к заказу | `POST /orders/:id/services`, `GET /orders/:id` → добавить JOIN `order_services` |
| CORS настроен жёстко | Использовать `env.API_CORS_ORIGIN` (уже сделано) |

### 4.2 Фронтенд

| Проблема | Решение |
|----------|---------|
| `useState` + `useEffect` в каждом компоненте | `react-query` (TanStack Query) для серверного состояния |
| Дублирование форм создания/редактирования | `react-hook-form` + Zod |
| Inline-стили в компонентах | Вынести в CSS-модули или Tailwind |
| Нет обработки ошибок сети | `ErrorBoundary` + `retry` |
| `sessionStorage` для токена | Оставить, но добавить refresh token |

### 4.3 DevOps

| Проблема | Решение |
|----------|---------|
| Нет тестов | Добавить: юнит-тесты (Vitest), интеграционные (Supertest) |
| Нет CI/CD | GitHub Actions: lint → test → deploy |
| Нет логирования ошибок | Sentry / свой логгер |
| Ручные миграции | `node-pg-migrate` уже есть, добавить `npm run migrate` в CI |

## 5. Порядок рефакторинга

```
Неделя 1: Шаг 1 (разбить api.ts) + Шаг 7 (разбить SettingsPage)
Неделя 2: Шаг 3 (DataTable) + Шаг 5 (KanbanBoard)
Неделя 3: Шаг 4 (FilterBar) + Шаг 8 (разбить DashboardPage)
Неделя 4: Шаг 2 (services на бэкенде)
Неделя 5: Шаг 6 (модалки) + Техдолг
```

**Правило:** рефакторинг делаем параллельно с доработками функционала (этап 3). Каждая новая фича реализуется уже по новой архитектуре, старый код рефакторится постепенно.
