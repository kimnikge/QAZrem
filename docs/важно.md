Приоритеты разработки и ограничения


#### ✅ Первая очередь (MVP, обязательно)
1. **Модели данных** – создать все таблицы из раздела 2 с ключами и индексами.
2. **Универсальный поиск** (`GET /search`) – логика из п.3.1 (поиск по имени, телефону, IMEI, модели).
3. **Создание заказа** (`POST /orders`) – с автоматическим созданием клиента/устройства, если не найдены.
4. **Смена статуса заказа** (`PATCH /orders/{id}/status`) – минимум статусы: `new`, `diagnosis`, `repair`, `ready`, `completed`. История изменений обязательна.
5. **Складской учёт** – таблицы `parts`, `order_parts`, `part_movements`. Списание запчастей (`POST /orders/{id}/parts`).
6. **Финансы** – приём платежей (`POST /payments`) и отчёт о прибыли за период (`GET /finance/report`).
7. **Роли** – разграничение доступа `admin`, `master`, `reception` через JWT.

#### ⏳ Вторая очередь (после запуска)
- Уведомления клиентов (Telegram/SMS) о смене статуса.
- Печать акта приёма-передачи (PDF).
- Прикрепление фото к заказу.
- Экспорт отчётов в Excel/CSV.
- Мобильная адаптация (PWA).

#### 🔮 Третья очередь (опционально)
- Аналитика и графики KPI.
- Интеграция с онлайн-кассой.
- API для внешних сервисов.

### 9.2 Ограничения (что можно и что нельзя)

#### ✅ Можно и рекомендуется
- Любая реляционная БД с транзакциями (PostgreSQL, MySQL 8+).
- Любой язык бэкенда – главное, читаемость кода.
- Логирование действий (`audit_log`).
- Индексы на поля поиска (`clients.phone`, `devices.imei`, `clients.name`).
- Мягкое удаление (`deleted_at`) вместо физического удаления.

#### ❌ Категорически нельзя (на боевом сервере)
1. **Хранить пароли в открытом виде** – в продакшене и в репозитории кода. В локальной разработке допускается упрощение (например, пароль `123`), но перед выкаткой все пароли должны быть захэшированы (bcrypt/Argon2).
2. **Списывать запчасть при отрицательном остатке** – проверка в транзакции.
3. **Менять статус заказа без записи в `order_history`**.
4. **Создавать дубликаты клиентов** – всегда искать по телефону/IMEI.
5. **Использовать одинаковые IMEI для разных устройств** – уникальность.
6. **Показывать мастеру закупочную цену** – поле `purchase_price` скрыто для роли `master`.
7. **Допускать SQL-инъекции** – только параметризованные запросы/ORM.
8. **Показывать финансовые отчёты не-админам** – только роль `admin`.
9. **Редактировать заказ в статусе `completed` или `cancelled`** – только чтение.

### 9.3 Технические реалии (не избыточно)
- **Сервер** – подойдёт любой VPS от $5/мес (1 vCPU, 1–2 GB RAM). Этого хватит для 5–10 одновременных пользователей.
- **Хранение файлов** – на старте локальная папка `uploads`, но с возможностью переключиться на S3.
- **Время ответа API** – не критично, но старайтесь держать в пределах 500 мс.
- **Резервное копирование** – ежедневный дамп БД (можно cron).
- **Логи** – хранить хотя бы 30 дней.

### 9.4 Бизнес-правила (логика работы)
- Один заказ = одно устройство.
- Предоплата не может быть больше полной стоимости заказа.
- Перевести заказ в `completed` можно только при статусе `ready` и полной оплате.
- При отказе от ремонта запчасти не списываются (но может быть оплачена диагностика – отдельный расход).
- Мастер не назначает себе зарплату – это делает админ через `expenses`.

### 9.5 Что тестировать в первую очередь
- Универсальный поиск (по телефону, IMEI, имени, частичному совпадению)
- Создание заказа с новым и существующим клиентом
- Списание запчасти: проверка остатка, невозможность уйти в минус
- Смену статусов (запрещённые переходы)
- Финансовый отчёт (сверка платежей и расходов)

## 10. Запрещающие действия и признаки автоматической генерации кода

### 10.1 Чего нельзя делать при разработке
- **Писать функции длиннее 200–250 строк** – такой код сложно читать и тестировать. Если функция перерастает этот объём, разбивайте её на несколько маленьких, каждая из которых решает одну задачу.
- **Создавать файлы с более чем 300 строками** – исключение делается только для файлов с чистыми конфигурациями (например, миграции БД или константы). Всё остальное требует разделения на модули по принципу единственной ответственности.
- **Использовать «магические числа» и строки** – все значения, кроме очевидных `0`, `1`, `-1`, должны быть вынесены в именованные константы.
- **Дублировать логику** – если один и тот же код встречается дважды, его нужно вынести в утилиту или сервис.
- **Прятать обработку ошибок в пустых `catch`/`except`** – каждая ошибка должна логироваться или хотя бы иметь осмысленное сообщение. «Тихие» подавления ошибок запрещены.
- **Использовать глобальные переменные для передачи состояния** – только локальные контексты, DI (dependency injection) или явные аргументы функций.
- **Оставлять закомментированный код в репозитории** – если код не нужен, его удаляют. Вернуть можно через систему контроля версий.
- **Пренебрегать аннотациями типов** – для Python обязательны type hints, для JS/TS – строгий режим и типы.

### 10.2 Как отличить код, сгенерированный ИИ, от человеческого (и что с этим делать)
ИИ часто оставляет характерные «следы», которые недопустимы в продакшене. Ниже перечислены признаки, по которым следует рефакторить или переписывать код, если он был создан автоматически.

| Признак | Пример (плохо) | Что нужно исправить |
|---------|----------------|----------------------|
| **Идеальные, но неестественные комментарии** | `# Increment counter by one` (очевидное) | Писать комментарии только там, где логика неочевидна. |
| **Избыточная абстракция** | Создание интерфейса с одним методом «на вырост» | Добавлять абстракции только когда реально нужно второе применение. |
| **Одинаковые паттерны именования** | Все переменные называются `temp`, `result`, `data` | Давать осмысленные имена: `updated_order`, `phone_number`, `device_id`. |
| **Слишком идеальное форматирование без единой опечатки** | Полное отсутствие случайных пробелов, переносов | Не страшно, но если код выглядит как «отутюженный» – пройдитесь форматтером и забудьте. Главное – функциональность. |
| **Пустые функции-обёртки** | `def get_client_id(client): return client.id` | Убирать такие прослойки, вызывать свойство напрямую. |
| **Чрезмерное комментирование каждого шага** | `# Now we check if status is completed` прямо перед `if status == 'completed'` | Удалять очевидные комментарии. Они засоряют код. |
| **Отсутствие обработки краевых случаев** | Функция предполагает, что `client.phone` всегда существует | Добавить проверки на `None`, пустые строки, нулевые значения. |
| **Шаблонные docstring** | `"""Функция для обработки заказа. Принимает заказ. Возвращает заказ."""` | Писать docstring только когда они несут пользу: описывают исключения, форматы данных, примеры. |

### 10.3 Рекомендации по организации кода (анти-перегруз)

#### Размер файлов
- **Максимум 250 строк** на один файл с логикой (модели, контроллеры, сервисы).
- **Файлы с миграциями БД** могут быть любыми – они генерируются автоматически и редко правятся руками.
- **Тестовые файлы** – допускается до 350 строк, так как тесты часто содержат повторяющиеся данные.

#### Принцип единственной ответственности
Каждый модуль отвечает **только за одну функцию**. Пример правильного разбиения для вашей CRM:

| Модуль | Ответственность |
|--------|------------------|
| `client_search.py` | Универсальный поиск клиентов (один эндпоинт `GET /search`) |
| `order_creation.py` | Создание заказа, валидация, вызовы к клиентам и устройствам |
| `order_status.py` | Смена статуса, запись в историю |
| `parts_stock.py` | Списание и приход запчастей, проверка остатков |
| `finance_payments.py` | Приём платежей, обновление предоплаты |
| `finance_report.py` | Формирование отчёта о прибыли |
| `auth_middleware.py` | JWT, проверка ролей |
| `db_models.py` | Описание всех таблиц (можно разбить на `models_client.py`, `models_order.py` и т.д., но не более 250 строк на файл) |
