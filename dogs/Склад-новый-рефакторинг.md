### Доработка 2. Корректировка остатка с аудитом (Блок 6.1)

**Проблема**
- Тип `correction` объявлен в `CHECK (part_movements.type)`, но API-эндпоинта нет.
- `PATCH /parts/:id` позволяет менять `quantity` напрямую (`updatePartSchema`) — остаток меняется без записи в `part_movements` и без сверки с партиями → рассинхрон `parts.quantity` и суммы `part_batches.current_quantity`.

**Что нужно**
- Новый `POST /parts/correction`: фактический остаток (или дельта ±), причина, документ.
- В транзакции: запись `part_movements(type='correction')` + синхронизация `parts.quantity` и партий (FIFO / служебная партия «Корректировка»).
- Убрать `quantity` из `PATCH /parts/:id` — запретить менять остаток в обход движения.

**Файлы**
- `backend/src/routes/parts.ts` (схемы + эндпоинт). Миграция не нужна — тип уже в CHECK.

**Реализовано (24.08.2026)**
- `POST /parts/correction` (admin): принимает `actual_quantity` ИЛИ `delta` (±), `reason/document`; в транзакции пишет `part_movements(type='correction')` и синхронизирует партии: увеличение → пополнение последней партии или служебная партия `CORR-*` (служебный поставщик «Служебная корректировка (система)»), уменьшение → FIFO-списание по партиям с ценами; защита от отрицательного остатка; ответ с `delta` и списком партий — ✅
- `PATCH /parts/:id` больше не меняет `quantity`: поле исключено из схемы (`omit`), а если клиент всё же шлёт — 400 с подсказкой использовать `/parts/correction` — ✅
- Хелперы `withdrawFromBatches` / `depositToBatch` / `getCorrectionSupplier` — ✅
- Фронтенд: `correctPart()` в `api/parts.ts`, секция «Корректировка остатка» в модалке редактирования запчасти (`PartsPage.tsx`) с полем фактического остатка и причиной — ✅
- Typecheck backend + frontend — ✅

### Доработка 3. Жизненный цикл резервов (Блок 6.1)

**Проблема**
- `reservations.status` поддерживает `used`, но нигде не выставляется.
- При списании на заказ (`assignPartToOrder` / `writeoffParts`) активные резервы не учитываются и не переводятся в `used` → зависшие `active`-резервы, доступный остаток уменьшается дважды (резерв + списание).
- `expires_at` не обрабатывается (нет автопротухания).

**Что нужно**
- В `order.service.ts`: при списании запчасти на заказ — если есть `active`-резерв на (part_id, order_id), перевести его в `used` (пропорционально количеству).
- При отмене заказа — авто-снятие всех активных резервов заказа (`cancelled`).
- (Опционально) фоновое протухание по `expires_at`.

**Файлы**
- `backend/src/services/order.service.ts`
- `backend/src/routes/orders.ts`

**Реализовано (24.08.2026)**
- `consumeReservations()` в `order.service.ts`: при списании (`assignPartToOrder` и `writeoffParts`) активные резервы (part_id + order_id) переводятся в `used`; при частичном использовании активный резерв уменьшается, использованная часть фиксируется отдельной записью `used` — ✅
- Отмена заказа (`updateOrderStatus` → `cancelled`): авто-снятие всех активных резервов заказа — ✅
- `expires_at`: в `POST /orders/:id/reserve` добавлен `BEGIN` и автопротухание истёкших резервов перед проверкой доступности; в `GET /orders/:id/reservations` добавлен флаг `is_expired` — ✅
- 28.08.2026: закрыта дыра — `expires_at` реально выставляется: поле в схеме резерва (опционально, ISO 8601), дефолт `NOW() + 7 дней` — ✅
- Typecheck backend — ✅
- Без миграций (схема уже была готова).

- **E2E (UI):** Playwright, `e2e/smoke.spec.ts`.
- **Существующие тесты для опоры:** `parts-warehouse.test.ts` (CRUD/движения), `warehouse-v2.test.ts` (категории, теги, FIFO, инвентаризация, резервы). Новые — отдельные файлы по блокам, не раздувая старые.
- **Паттерн фикстур:** `beforeAll` — логин админа (env или дефолт `MISTIK-XXX` / `Detka0300304345`), создание уникальных фикстур (`TEST-...-${Date.now()}`); `afterAll` — `closePool()`.

### Чек-лист каждого теста

- [ ] `beforeAll`: логин админа; создание уникальных фикстур (`TEST-...-${Date.now()}`), чтобы прогоны не конфликтовали
- [ ] Проверка кодов ответов: 200/201/400/403/404/409/422
- [ ] После каждой операции — проверка `parts.quantity` и записей в `part_movements`
- [ ] Транзакционность: ошибка в середине операции → остатки не изменились (ROLLBACK)
- [ ] `afterAll`: `closePool()`
- [ ] Для доработок 3–4: замокать внешние сервисы (Telegram/WhatsApp), не ходить в сеть
- [ ] E2E-смоук по ключевым UI-сценариям (создание запчасти, оприходование, инвентаризация) — расширить `e2e/smoke.spec.ts`
